<Layer kind="concept">

Tools fail. A network call times out, a test runner crashes, a file is locked. A harness decides what happens next, at three levels:

1. **Retry** the same call, after a wait that grows each time (**exponential back-off**: here 500 ms, then 1 s, then 2 s), up to a **retry budget**. The model never sees a failure that a retry fixed.
2. When the budget is spent, **feed the error back** to the model as the tool's result, and let it decide. The scripted model here does what models often do: it tries the same call again.
3. **Detect loops**: three identical calls in a row are not progress. The harness either **stops** the run or **nudges** the model with a message telling it to try something else.

Seed 0, with no retries, shows the failure: the shell fails twice in a row, the model asks for the same `pytest` a third time, and loop detection stops the run after <V of="recovery.r0-stop.elapsed" fmt="ms" />, with the bug unfixed. One retry is not enough for this seed either. With two, the retries absorb every failure and the run finishes in <V of="recovery.r2-stop.elapsed" fmt="ms" /> after <V of="recovery.r2-stop.retries" fmt="int" /> retries: slower than a lucky run, because waiting is the price of a retry.

Now set the budget to 0 and choose **nudge**. The run "finishes": the nudge moves the model on, it edits the file, the last test run fails again, and the model reports that all the tests pass. The run's status is done; the tests never passed. A harness that counts "the model said it was done" as success will report this run as a success. Counting only runs whose last test run passed tells the truth, and that is what the chart below does.

</Layer>

<Callout kind="illustrative">

The shell's failure rate (30% of attempts, independent, seeded), the back-off schedule and the tool times are illustrative; real failures are often not independent (a service that is down stays down, and retrying it only adds load), which is what back-off and a budget protect against. The scripted model always repeats a failed call; a real model may try something else first.

</Callout>

<Layer kind="maths">

If each attempt fails independently with probability $p$, a call with a budget of $r$ retries fails only when all $r+1$ attempts do:

$$
P_{\text{call}} = 1 - p^{\,r+1},
$$

so with $p$ = <V of="recovery.model.p" fmt="num" />, one call succeeds with probability <V of="recovery.model.0.call" fmt="num" />, <V of="recovery.model.1.call" fmt="num" /> and <V of="recovery.model.2.call" fmt="num" /> for 0, 1 and 2 retries. A run is a chain of calls: here the model repeats a failed test run, and loop detection allows two identical calls in a row, so a test step is lost only when two calls in a row fail, with probability $q^2$ where $q = p^{\,r+1}$. The task has two test steps:

$$
P_{\text{run}} = (1 - q^2)^2 ,
$$

which predicts <V of="recovery.model.0.run" fmt="pct" />, <V of="recovery.model.1.run" fmt="pct" /> and <V of="recovery.model.2.run" fmt="pct" />; the 100 seeded runs measured <V of="sweeps.recovery.stop.0.success" fmt="pct" />, <V of="sweeps.recovery.stop.1.success" fmt="pct" /> and <V of="sweeps.recovery.stop.2.success" fmt="pct" />, within sampling error (about ±4 points at 100 runs). The price is time: the waits before retry $k$ are $b f^{k}$, so a call that uses its whole budget waits $T_{\text{wait}} = b\,(f^{r}-1)/(f-1)$, here <V of="recovery.model.2.backoff" fmt="ms" /> for two retries and <V of="recovery.model.4.backoff" fmt="ms" /> for four, on top of the failed attempts themselves.

</Layer>
